# AgentWeave 认证与权限子系统演进路线图

## 1. 文档目标与读者

本文档用于说明 AgentWeave 认证与权限子系统的后续演进方向，帮助维护者和开发者理解：

- 当前这套“可关闭认证 + Session + RBAC”方案为什么适合当前项目
- 它目前的主要治理短板是什么
- 后续应该如何逐步增强安全边界，而不是一次性过度设计

## 2. 一句话结论

认证与权限子系统当前应继续沿“可选认证 + 服务端 Session + 本地 RBAC”方向稳步增强，优先统一权限边界和敏感操作保护，再考虑更复杂的隔离模型。

## 3. 当前状态

当前系统已经实现：

- 认证总开关
- OIDC / SSO 登录
- 本地固定管理员账号登录
- SessionMiddleware 承载登录态
- 本地 `User / Role / Permission` 模型
- REST 路由权限保护
- WebSocket 写权限保护
- 前端认证状态加载与权限感知

这说明当前子系统已经满足“演示和平台工作台所需的基础安全边界”。

## 4. 当前短板

- 权限粒度虽然已经覆盖主要子系统，但仍偏资源级，缺少更强的操作级语义。
- 审计能力较弱，难以追踪谁改了什么配置、谁测试了什么外部能力。
- 当前登录模型仍偏平台单管理员 / 外部 SSO，缺少更完整的本地用户管理能力。
- 前端虽然具备权限感知，但不同子系统对权限的展示和交互控制还可以进一步统一。
- 多租户或更强域隔离尚未进入当前模型。

## 5. 演进原则

### 5.1 后端是真正安全边界

前端权限控制只是体验层优化，真正的安全判断必须继续在后端完成。

### 5.2 先统一权限边界，再细化权限粒度

如果不同子系统对权限命名和作用边界理解不一致，细化粒度只会放大复杂度。

### 5.3 让敏感操作优先获得更强保护

并不是所有功能都需要同样强的控制。应优先关注配置写入、工具测试、外部能力绑定、凭证相关操作等高风险动作。

### 5.4 不为未来想象中的复杂组织结构过度设计

当前项目仍是平台示例和本地工作台，演进路径应与现实复杂度相匹配。

## 6. 阶段路线图

### 6.1 Phase 1：把登录、角色和权限保护做稳

**目标**

确保当前认证开关、登录入口、角色种子数据和权限保护链路稳定可靠。

**重点**

- 统一登录方式的行为差异
- 继续巩固 REST / WS 保护
- 明确角色和权限的最小语义边界

### 6.2 Phase 2：统一 REST / WS / 子系统权限边界

**目标**

让不同子系统在权限语义上更一致，减少“路由有保护、界面无提示”或“界面隐藏了、后端含义不清”的问题。

**重点**

- 梳理全局权限矩阵
- 收敛子系统权限命名
- 统一前后端权限感知方式

### 6.3 Phase 3：增强敏感操作保护、审计和最小权限

**目标**

对更高风险的操作引入更明确的记录和限制。

**重点**

- 配置修改与外部能力测试的操作审计
- 最小权限原则
- 更清晰的高风险操作保护策略

### 6.4 Phase 4：为更复杂隔离场景预留能力

**目标**

在不立即引入复杂模型的前提下，为未来更强的隔离需求预留接口和设计空间。

**重点**

- 更强的域隔离或租户隔离前置条件
- 更细的用户来源和权限边界
- 更清晰的跨子系统安全治理模型

## 7. 每阶段进入条件与完成标准

| 阶段 | 建议进入条件 | 建议完成标准 |
| --- | --- | --- |
| Phase 1 | 当前认证功能可用，但规则还主要依赖代码阅读理解 | 登录、角色、权限边界稳定清晰 |
| Phase 2 | 核心登录链路稳定后，跨子系统权限一致性成为主要问题 | REST、WS 和前端权限语义更一致 |
| Phase 3 | 边界统一后，敏感操作和审计需求开始凸显 | 高风险操作具备更明确的保护和追踪能力 |
| Phase 4 | 当前平台开始需要更强隔离模型 | 已具备进入更复杂安全模型的清晰前置条件 |

## 8. 关键风险与非目标

### 8.1 关键风险

- 若权限继续只做最小保护而缺少说明，后续平台能力增长后会难以治理。
- 若过早引入复杂 IAM 模型，会超出当前项目复杂度。
- 若把权限判断分散到前端逻辑中，会削弱后端安全边界。

### 8.2 非目标

- 当前不将系统扩展成完整企业身份管理平台。
- 不在这一阶段引入复杂的审批流。
- 不在没有真实需求前提前实现多租户安全架构。

## 9. 推荐优先级

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 现在就做 | 梳理全局权限矩阵和边界说明 | 这是后续治理的基础 |
| 现在就做 | 校验 REST / WS / 前端权限语义一致性 | 当前最直接影响正确性 |
| 接下来做 | 敏感操作保护与审计 | 适合在边界稳定后增强 |
| 之后再做 | 更强的隔离模型准备 | 应建立在真实场景需求之上 |

## 10. 下一步执行建议

建议按以下顺序推进：

1. 先整理当前角色与权限的全量映射表。
2. 再审视各子系统路由与前端界面是否一致遵循该映射。
3. 明确哪些操作属于高风险动作，并优先补强这些动作的审计和保护。
4. 在此基础上，再考虑是否需要进入更复杂的用户和隔离模型。
