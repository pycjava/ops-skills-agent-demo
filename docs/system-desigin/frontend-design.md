# Frontend 模块设计说明

## 1. 设计目标

前端的目标不是简单展示聊天记录，而是把多 Agent、多面板、多种异步能力收敛成一个连贯的工作台。它需要同时处理：

- 实时会话和流式消息更新。
- Agent 切换与 Skills 可见性变化。
- 任务抽屉、通知中心、MCP 面板、记忆面板等辅助工作流。
- 登录状态与权限门禁。

## 2. 页面与路由结构

前端采用单工作台结构，路由层尽量简单：

- `RootApp.vue`：应用根节点。
- `router.ts`：定义 `/login` 和工作台主路由，并处理登录守卫。
- `views/LoginPage.vue`：认证入口。
- `App.vue`：主工作台，承载绝大多数业务交互。

这种设计的核心思想是：**将复杂度主要沉到状态管理和组件拆分，而不是分散到多个页面路由**。

## 3. 工作台布局

`App.vue` 组织了系统的主要界面区域：

- 左侧会话列表。
- 中间消息区。
- 底部输入区。
- 右侧能力面板（Skills / MCP / Memory）。
- 任务抽屉。
- 任务提醒中心。
- MySQL 实例选择弹窗等上下文组件。

布局设计强调“主链路优先、辅助面板按需展开”：

- 对话仍然是中心。
- 任务、提醒和配置不打断主消息流，但与其保持可跳转关系。

## 4. 状态管理设计

### 4.1 顶层 Store 聚合

`frontend/src/stores/chat.ts` 是前端状态聚合入口，负责：

- 定义跨域共享的 `ref` 与 `computed`。
- 创建多个领域 domain。
- 组合对外暴露的统一接口。

顶层 Store 的定位更接近“状态编排器”，而不是把所有逻辑都塞在一个文件中。

### 4.2 领域拆分

`frontend/src/stores/chat/` 目录按领域拆分为多个模块：

- `conversations.ts`：会话列表、当前会话、历史消息、Agent 草稿选择。
- `socket.ts`：WebSocket 生命周期、消息发送、流式事件消费。
- `attachments.ts`：附件上传、会话附件列表、待发送附件快照。
- `tasks.ts`：任务列表、草稿、执行记录、任务流式回放。
- `notifications.ts`：提醒列表、未读数、已读状态同步。
- `mcp.ts`：MCP 配置读写、测试与可见列表。
- `memory.ts`：记忆树、文档内容、删除和报告/记忆产物联动。
- `auth.ts`：认证状态、当前用户、权限判断、登录方式。
- `helpers.ts` 与 `types.ts`：共享工具与类型。

这种结构的优势是：

- 每个域逻辑集中。
- 顶层组合接口保持统一。
- 组件只依赖所需动作和状态，而不需要知道全部后端细节。

## 5. 组件职责设计

### 5.1 页面级组件

- `App.vue`：主工作台、交互编排和面板开关。
- `LoginPage.vue`：登录页和登录方式入口。

### 5.2 业务组件

- `ConversationList.vue`：会话切换、新建会话、标题展示。
- `ConversationTitleEditor.vue`：会话标题编辑。
- `MessageBubble.vue`：文本消息、工具消息、报告下载入口与思考展示。
- `ConversationAttachmentBar.vue`：会话附件展示和删除。
- `TaskDrawer.vue`：任务列表、草稿编辑、执行记录和手动触发。
- `TaskNotificationCenter.vue`：提醒列表、未读数和已读操作。
- `SkillPanel.vue`：当前 Agent 可见 Skills。
- `McpPanel.vue`：MCP Server 列表、配置文本、连接测试。
- `MemoryPanel.vue` / `MemoryTreeNode.vue`：记忆树浏览、文档打开、删除。
- `MysqlInstanceSelectorDialog.vue`：云实例候选选择。

组件拆分遵循一个原则：**把可独立测试和可独立复用的交互块抽出来，但把跨域编排保留在 `App.vue`**。

## 6. 核心交互流程

### 6.1 应用初始化

`useAppChrome.ts` 负责工作台初始化流程，典型顺序是：

```text
页面加载
  -> 读取主题和界面状态
  -> 拉取认证状态
  -> 拉取 Agent 列表
  -> 拉取会话列表
  -> 连接 WebSocket
  -> 按权限加载通知、Skills、MCP、记忆树
```

设计原因：

- 先确认认证和权限，再决定哪些面板可见。
- 先拿 Agent 列表，再让后续会话、Skills 和默认 Agent 行为保持一致。

### 6.2 发送消息

`useChatComposer.ts` 负责输入框交互：

- 自动调整输入框高度。
- 处理 `@skill` 提示与补全。
- 区分显示给用户的消息内容与发送给后端的内容。
- 根据当前消息内容自动注入隐式 Skill 提示。

典型流程：

```text
用户输入
  -> 检测 @mention
  -> 组装最终发送内容
  -> socket.sendMessage(...)
  -> 本地插入用户消息
  -> 等待服务端流式更新助手消息
```

### 6.3 流式消息渲染

`socket.ts` 负责把 WebSocket 事件转成消息状态：

- `text_delta`：拼接助手文本。
- `thinking_delta`：更新思考内容。
- `tool_call`：插入工具调用气泡。
- `tool_result`：插入工具结果气泡，并识别报告/记忆产物。
- `routing`：提示正在切换子 Agent 或升级任务。
- `done`：结束当前轮对话 loading。
- `error`：补充错误消息并终止当前加载态。

这意味着前端展示的不是简单的“回复完成后再渲染”，而是一个完整的执行过程。

### 6.4 任务交互

任务交互分为两条链路：

- **聊天内生成任务**：从消息中识别任务意图、生成草稿、让用户确认。
- **任务抽屉管理任务**：查看任务列表、编辑任务、手动触发和查看执行记录。

`tasks.ts` 还负责通过 SSE 读取：

- 从会话消息生成任务时的增量事件。
- 某次任务运行会话的历史 + 增量回放。

### 6.5 右侧能力面板

右侧面板采用 Tab 结构，在 `skills`、`mcp`、`memory` 三类信息间切换。

其设计目的不是提供“另一个设置页”，而是让用户在同一工作台中可见：

- 当前 Agent 会什么。
- 当前系统接了哪些工具。
- 当前已有的长期记忆和报告。

## 7. 权限与可见性设计

前端通过 `auth.ts` 和顶层 `hasPermission()` 控制：

- 是否显示登录门禁。
- 是否允许发送消息。
- 是否允许上传附件。
- 是否允许打开任务、提醒、MCP、记忆和 Skills 面板。

这里的重点是：

- 前端用权限做体验控制和显隐。
- 后端仍然保留最终校验，避免仅靠前端保护。

## 8. 数据与状态同步策略

### 8.1 REST + WebSocket 双通道

- REST 用于结构化资源管理，例如会话列表、任务列表、MCP 配置和记忆树。
- WebSocket 用于高频增量消息。
- SSE 用于任务草稿生成和任务运行回放等“单次长流程”。

使用三种通道而不是单一协议的原因是：

- 每类数据的交互模式不同。
- 这样能让前端状态更新语义更清晰。

### 8.2 局部缓存与刷新

- 会话和消息由当前选择状态驱动。
- 记忆树支持已加载标记和强制刷新。
- 任务提醒维护未读数，避免每次都全量重算。
- 某些面板仅在用户有权限时才触发加载。

## 9. 异常与兜底设计

- WebSocket 未连接或正在加载时禁用发送。
- 登录未完成时展示工作台门禁，而不是半可用界面。
- 任务流、记忆读取、MCP 测试等失败时都保留独立错误状态，避免一个面板的错误污染整个应用。
- 当选中的记忆文件已不存在时，自动回退到第一份可用文档。

## 10. 设计取舍

- 使用单页工作台简化整体导航，但 `App.vue` 承担了较强的编排职责。
- 使用顶层 Store 聚合多个 domain，利于一致性，但要求每个 domain 边界清晰。
- 使用多通道交互（REST / WebSocket / SSE）提高适配性，但增加了状态同步复杂度。

## 11. 演进方向

- 继续把 `App.vue` 中偏编排的逻辑下沉到 composable 或 domain。
- 为长对话和大消息列表增加更强的虚拟滚动或增量加载策略。
- 为任务运行、报告下载和记忆产物增加更统一的 artifact 视图模型。
