# 定时任务与任务提醒设计

## 1. 设计目标

任务子系统用于把一次性的聊天请求演进为可重复执行、可追踪、可提醒的后台任务。它的目标包括：

- 从会话中识别“定时巡检 / 定时执行”意图。
- 让任务定义、任务运行和任务提醒成为三个独立但可关联的对象。
- 让任务结果复用现有会话消息链路，而不是再造一套报告展示系统。
- 为前端提供任务草稿、运行记录和通知中心等完整闭环。

## 2. 子系统边界

任务子系统覆盖以下能力：

- 任务草稿生成与确认。
- 任务 CRUD。
- 调度器轮询与触发执行。
- 运行记录创建与状态更新。
- 执行会话回放。
- 完成/失败通知。

它不负责：

- 通用的分布式调度。
- 复杂的任务依赖 DAG。
- 大规模重试、隔离队列和优先级调度。

## 3. 核心对象设计

### 3.1 `InspectionTask`

任务定义对象，关注长期稳定的配置：

- `name`：任务名称。
- `source_conversation_id`：来源会话。
- `agent_id`：执行任务的 Agent。
- `skill_id`：可选的主 Skill 标识。
- `prompt_template`：执行提示模板。
- `target_payload`：结构化目标信息。
- `schedule_type` / `cron_expr`：调度表达式。
- `enabled`：是否启用。
- `last_run_at` / `next_run_at` / `last_status`：最近执行状态。

### 3.2 `InspectionTaskRun`

单次执行记录对象，关注一次运行实例：

- `task_id`：所属任务。
- `trigger_type`：触发方式，如手动触发或调度触发。
- `status`：运行状态。
- `conversation_id`：该次执行对应的运行会话。
- `started_at` / `finished_at`：运行时刻。
- `error_message`：失败信息。
- `report_name` / `report_path`：产物引用。

### 3.3 `TaskNotification`

异步提醒对象，关注用户可见的提醒投递：

- 关联 `task_id` 与 `task_run_id`。
- `status`：成功或失败。
- `title` / `summary`：任务摘要。
- `report_name` / `report_path`：可下载报告入口。
- `read_at`：是否已读。

三者拆分的价值是：

- 任务定义可以长期存在。
- 同一任务可累积多次运行。
- 通知可以按需生成、已读和过滤，而不污染执行记录本身。

## 4. 后端模块划分

### 4.1 路由层

`backend/api/routers/inspection_tasks.py` 提供：

- 任务列表查询。
- 任务详情。
- 创建 / 更新 / 删除任务。
- 从会话消息生成任务草稿或直接创建任务。
- 手动触发任务。
- 运行记录查询。
- 某次运行会话的 SSE 回放。

`backend/api/routers/task_notifications.py` 提供：

- 通知列表。
- 单条已读。
- 全部已读。

### 4.2 服务层

`services/inspection_task_llm.py` 负责：

- 分析消息是否命中任务创建意图。
- 从上下文提炼任务模板。

`services/inspection_tasks.py` 负责：

- 构建任务草稿。
- 创建、更新、删除任务。
- 计算下次执行时间。
- 执行任务并维护运行记录。

`services/inspection_scheduler.py` 负责：

- 启动后台轮询循环。
- 查找到期任务。
- 调用执行逻辑。

`services/task_notifications.py` 负责：

- 从运行会话中抽取摘要。
- 识别最新报告产物。
- 生成提醒事件和未读数。

## 5. 任务创建流程

### 5.1 聊天内生成草稿

```text
用户在会话中提出“定时巡检”诉求
  -> 后端分析消息中的任务意图
  -> 若命中，抽取任务名称、调度表达式、Agent、目标内容
  -> 返回任务草稿
  -> 前端在任务抽屉中展示草稿供用户确认
```

这样设计的原因是：任务通常来自当前会话上下文，直接复用上下文比让用户重新填写表单更自然。

### 5.2 直接创建与澄清

当分析结果足够明确时，可直接创建任务；当信息不足时，返回：

- `clarification_needed`
- 澄清提示
- 当前任务意图分析结果

这让任务创建既能自动化，也能避免不完整配置直接进入调度器。

## 6. 任务执行流程

### 6.1 调度触发

```text
InspectionSchedulerRuntime 启动
  -> 周期性扫描 next_run_at <= 当前时间 的启用任务
  -> 为每个任务创建 InspectionTaskRun
  -> 创建运行会话
  -> 使用任务绑定的 Agent 执行 prompt_template
```

### 6.2 运行会话复用

每次任务运行都会创建一个新的 `Conversation`，并在其中写入消息。这样做的好处是：

- 任务执行结果天然可回放。
- 前端可以复用消息渲染和 artifact 展示能力。
- 普通聊天和后台任务共用同一种结果表达模型。

### 6.3 运行结束

```text
任务执行完成
  -> 更新 InspectionTaskRun.status / finished_at
  -> 更新 InspectionTask.last_run_at / next_run_at / last_status
  -> 提取报告路径和摘要
  -> 生成 TaskNotification
```

## 7. 前端交互设计

### 7.1 任务抽屉

`TaskDrawer.vue` 承载：

- 任务列表。
- 任务草稿确认与编辑。
- 任务启停与删除。
- 运行记录列表。
- 手动触发。
- 任务运行会话查看入口。

### 7.2 任务流式回放

前端通过 `tasks.ts` 订阅任务运行 SSE：

- 先接收历史消息。
- 再接收新增消息。
- 同步接收 `run_status`。

这样既支持回看历史任务，也支持观看正在执行的任务。

### 7.3 任务提醒中心

`TaskNotificationCenter.vue` 用来承载：

- 未读提醒数。
- 成功/失败摘要。
- 报告下载入口。
- 已读操作。

提醒中心与任务抽屉分离，是为了区分“配置任务”和“消费结果”两种心智模型。

## 8. 通知设计

通知生成依赖运行会话中的真实消息，而不是单独拼装结果。服务层会：

- 找到最后一条有效助手文本作为摘要候选。
- 识别最近的报告引用。
- 根据运行状态填充标题、摘要和下载信息。

这样可以保证通知内容与真正执行结果一致，而不是复制一套并行摘要逻辑。

## 9. 失败场景与兜底策略

### 9.1 创建阶段

- 若任务意图未命中，返回 `not_task_creation`。
- 若信息不完整，返回澄清提示，不直接创建任务。
- 若配置非法，前端展示错误并保持当前草稿。

### 9.2 执行阶段

- 运行失败时写入 `error_message`。
- 任务运行状态更新为失败。
- 仍然生成失败通知，避免后台静默失败。

### 9.3 回放阶段

- 如果运行记录不存在或未生成会话，后端返回显式错误。
- 前端在 SSE 失败时保留错误状态，不污染任务列表本身。

## 10. 与其他子系统的关系

- 与会话系统：任务运行结果复用消息模型和会话展示。
- 与 Agent Runtime：任务决定执行哪个 Agent 与哪种 prompt。
- 与记忆系统：任务运行可能生成 `/memories/reports/` 下的报告。
- 与权限系统：任务读写、触发和通知读取均受 RBAC 保护。

## 11. 设计取舍

- 使用轮询调度器实现简单、可控，但不适合高精度或大规模任务场景。
- 使用运行会话复用现有消息模型，减少重复实现，但要求消息结构足够通用。
- 将通知单独建模增强异步体验，但引入了额外已读状态同步成本。

## 12. 演进方向

- 引入重试、超时和失败分类。
- 为任务增加更多模板化结构，而不只是巡检类任务。
- 为通知和报告引入更统一的 artifact 元数据。
- 在保持接口兼容的前提下，逐步升级为更专业的调度框架。
