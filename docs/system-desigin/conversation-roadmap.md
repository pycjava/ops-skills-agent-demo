# AgentWeave 会话子系统演进路线图

## 1. 文档目标与读者

本文档用于说明 AgentWeave 会话子系统的后续演进方向，既帮助非研发读者理解“会话体验接下来优先补什么”，也帮助研发团队明确阶段目标、风险和优先级。

本文档与 `conversation-design.md` 的关系是：

- `conversation-design.md` 说明当前实现
- 本文档说明为什么按当前顺序演进，以及下一步建议先做什么

## 2. 一句话结论

会话子系统当前最重要的任务不是继续堆叠新功能，而是先把会话模型、流式事件协议和附件上下文体验做稳，再逐步增强回放、观测和治理能力。

## 3. 当前状态

当前会话子系统已经具备以下基础能力：

- 支持会话列表、切换、删除和标题修改
- 支持基于 REST 的历史消息读取
- 支持基于 WebSocket 的实时对话和事件流
- 支持会话级附件上传、删除和消息快照
- 支持任务运行会话回放
- 支持在前端统一渲染文本、思考、工具调用、工具结果和错误消息

这说明会话子系统已经从“简单聊天 Demo”演进成了平台级主交互层，但它的协议和可观测性仍偏轻量。

## 4. 当前短板

- 流式事件协议仍包含较多专用分支，例如路由、OCR、任务通知等，通用性和可维护性一般。
- 消息类型较粗，历史消息和运行时事件之间仍存在语义映射成本。
- 当前连接断开后仅能重连，缺少更强的断点恢复或运行态回放能力。
- 附件上下文已接入主链路，但对用户而言“本轮用了哪些附件、OCR 结果是否复用”仍然不够透明。
- 会话级观测不足，难以回答某轮对话耗时为何较长、何处失败、哪些工具参与了执行。

## 5. 演进原则

### 5.1 先稳定协议，再扩展体验

在会话子系统中，事件协议比组件样式更基础。任何新的聊天体验都应优先建立在更稳定的协议之上。

### 5.2 保持历史回放与实时体验尽量一致

用户不应该因为内容来自“实时对话”还是“任务回放”而看到完全不同的模型。后续演进应继续收敛这两条链路。

### 5.3 让附件成为显式上下文，而不是隐式副作用

附件和 OCR 结果应逐步从“系统内部知道用了什么”演进为“用户也能清楚看到本轮基于哪些材料做出结论”。

### 5.4 增强能力不应破坏主聊天链路

清空、删除、回放、通知、OCR 等能力都应作为增强层存在，不应让主聊天流程更加脆弱。

## 6. 阶段路线图

### 6.1 Phase 1：稳定会话与消息模型

**目标**

把会话、消息、附件快照和任务运行会话之间的模型关系彻底稳定下来。

**重点**

- 明确各类消息的语义边界
- 统一普通会话与任务运行会话的最小公共字段
- 收敛标题、来源、附件快照等基础模型约束

**为什么先做**

如果模型层不稳定，后续所有协议治理和前端体验都会建立在变动基础上。

### 6.2 Phase 2：完善流式事件协议与前后端同步

**目标**

减少事件协议中的特例分支，让前后端对同一类运行事件形成更统一的约定。

**重点**

- 梳理 WebSocket 事件类型
- 统一系统消息、路由消息、工具消息的表达方式
- 降低前端对“最近一次工具输入”这类补偿逻辑的依赖

**为什么排在这里**

会话模型稳定后，协议才有明确收敛目标。

### 6.3 Phase 3：增强附件上下文与运行会话体验

**目标**

让附件、OCR、任务回放和会话上下文在用户界面中更明确、更易理解。

**重点**

- 明示本轮消息使用了哪些附件和 OCR 结果
- 优化运行会话回放体验
- 更好地区分“聊天会话”和“任务运行会话”的来源信息

### 6.4 Phase 4：引入更强的会话观测、回放和治理能力

**目标**

让会话子系统具备更强的调试和治理能力，而不仅仅是展示消息。

**重点**

- 会话级耗时、错误、工具链路观测
- 更强的流式回放和问题定位能力
- 更明确的系统事件与用户可见事件边界

## 7. 每阶段进入条件与完成标准

| 阶段 | 建议进入条件 | 建议完成标准 |
| --- | --- | --- |
| Phase 1 | 当前消息和会话模型已经能稳定支撑主流程，但历史与流式映射仍偏松散 | 主要消息类型、来源字段和附件快照语义稳定，不再频繁调整 |
| Phase 2 | 模型层稳定后，协议复杂度开始成为前后端协作成本 | 事件类型和前后端映射关系更统一，特殊补偿逻辑减少 |
| Phase 3 | 协议已足够稳定，主要问题转向用户对附件和回放体验的理解成本 | 用户能更清楚感知当前轮上下文、附件来源和任务运行来源 |
| Phase 4 | 主链路体验稳定，团队开始需要更强的问题定位和治理能力 | 具备基础会话观测、回放和系统事件治理能力 |

## 8. 关键风险与非目标

### 8.1 关键风险

- 若过早追求复杂交互效果，可能加重现有协议负担。
- 若消息类型继续无序扩张，历史回放和实时流将越来越难统一。
- 若前端持续承担过多事件修正逻辑，会放大协议变更成本。

### 8.2 非目标

- 本路线图不试图把会话系统演进成完整客服工单系统。
- 不在当前阶段引入复杂的多端同步机制。
- 不把所有观测问题都放到前端解决。

## 9. 推荐优先级

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 现在就做 | 梳理消息模型和事件类型 | 这是后续协议和回放体验的基础 |
| 现在就做 | 明确附件快照和会话来源语义 | 避免后续文档和实现各自理解不同 |
| 接下来做 | 收敛 WebSocket 事件协议 | 减少前后端分支逻辑 |
| 接下来做 | 强化附件和任务运行会话的可见性 | 提升用户理解成本 |
| 之后再做 | 会话观测和高级回放 | 建立在前面阶段稳定后再推进更合适 |

## 10. 下一步执行建议

建议从以下几项开始：

1. 先整理当前 WebSocket 事件和 `Message.type` 的映射表。
2. 再梳理 `Conversation` 的来源字段和任务运行会话的边界。
3. 明确附件快照、OCR 结果和最终回答之间的可追溯关系。
4. 在此基础上，再决定协议收敛和前端体验增强的优先顺序。
