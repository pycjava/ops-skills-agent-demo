# AgentWeave 长期记忆与报告子系统演进路线图

## 1. 文档目标与读者

本文档用于说明 `/memories/` 与报告产物这一子系统的后续演进方向，帮助维护者和开发者理解：

- 当前为什么继续保持“统一文件树”方案
- 这个方案的短板主要在哪里
- 什么时候应从文本文件管理进入更强的元数据和结构化层

## 2. 一句话结论

长期记忆与报告子系统当前最适合继续沿“统一路径空间 + 轻量文件树 + 与任务/RAG 联动”的方向演进，优先补齐元数据、分类和检索质量，再逐步进入结构化对象和更强的系统联动。

## 3. 当前状态

当前该子系统已经实现：

- 通过 `/memories/` 暴露长期内容
- 基于 LangGraph Store 维护 memory 文件树
- 前端支持记忆树浏览、内容预览和删除
- 报告可统一写入 `/memories/reports/`
- 任务运行和任务通知可引用报告路径
- Memory 写删会尝试同步到 RAG

这说明它已经是平台中“长期内容沉淀层”的基础实现。

## 4. 当前短板

- memory 与 report 的元数据仍然偏少，难以按类型、来源、时间或归属做更细管理。
- 前端当前更偏只读浏览，缺少更完整的写入、编辑和管理体验。
- 报告引用主要依赖路径和工具事件推断，规则简单但不够强壮。
- 对报告的归档、保留和清理缺少明确策略。
- 高价值对象仍主要以文本形式沉淀，尚未形成结构化知识层。

## 5. 演进原则

### 5.1 继续以统一路径空间为核心

在当前阶段，`/memories/` 仍应保持“统一长期内容入口”的角色，避免过早拆成多个孤立系统。

### 5.2 元数据治理优先于复杂功能

在没有足够元数据之前，搜索、过滤、结构化和生命周期管理都会受限。

### 5.3 报告必须保持可引用、可下载、可追溯

报告不仅是文件，更是任务执行结果的一部分。后续演进必须保持它与任务、通知和 RAG 的连接。

### 5.4 结构化应从高价值对象开始

并非所有 memory 文件都值得结构化。应优先选择实例、环境、凭证、任务、报告摘要这类高价值对象。

## 6. 阶段路线图

### 6.1 Phase 1：规范 memory 与报告的目录、读写和展示

**目标**

先把当前统一路径空间方案稳定下来，明确目录、读写入口和展示边界。

**重点**

- 明确共享记忆、Agent 私有记忆和报告目录约定
- 收敛报告命名与落盘规则
- 统一前端展示语义

### 6.2 Phase 2：补齐元数据、分类和检索质量

**目标**

让 memory 与 report 从“文件能看见”提升为“内容能被管理、筛选和稳定检索”。

**重点**

- 增加文件类型、来源、时间、归属和标签等元数据
- 提升 RAG 对 memory / report 的检索效果
- 改善报告和普通 memory 的区分能力

### 6.3 Phase 3：沉淀高价值结构化对象与报告摘要层

**目标**

让高价值内容开始从纯文本沉淀转向“文本 + 结构化对象”的双层表达。

**重点**

- 抽取高价值对象
- 为报告建立更稳定的摘要层
- 让系统优先复用结构化结果，再回退到原始文档

### 6.4 Phase 4：和 RAG / GraphRAG / 任务系统形成更强联动

**目标**

把长期记忆与报告真正变成平台级知识资产，而不是只是静态文件目录。

**重点**

- 和更强的 RAG / GraphRAG 联动
- 和任务系统形成更强的引用链
- 支撑更复杂的跨文档关系问答

## 7. 每阶段进入条件与完成标准

| 阶段 | 建议进入条件 | 建议完成标准 |
| --- | --- | --- |
| Phase 1 | 当前文件树已可用，但目录和写入规则仍主要靠约定 | memory / report 的目录、命名和展示边界清晰 |
| Phase 2 | 当前最主要问题转向查找、分类和检索质量 | 元数据足以支撑分类、过滤和更稳定的检索 |
| Phase 3 | 元数据稳定后，出现大量高价值对象问答需求 | 已形成一批稳定的结构化对象和报告摘要层 |
| Phase 4 | 结构化层已有实际收益，开始需要更强的系统联动 | memory / report 与任务、RAG、图检索形成更强闭环 |

## 8. 关键风险与非目标

### 8.1 关键风险

- 如果目录规范和命名规则不稳定，报告引用链会越来越脆弱。
- 如果元数据治理长期缺位，后续结构化和 GraphRAG 的成本会被放大。
- 如果把所有 memory 都强行结构化，复杂度会高于收益。

### 8.2 非目标

- 当前不把 memory 子系统演进成完整文档管理平台。
- 不在这一阶段引入复杂的文档审批或版本工作流。
- 不要求所有报告都立即具备结构化表示。

## 9. 推荐优先级

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 现在就做 | 明确目录与报告命名规范 | 这是所有后续能力的基础 |
| 现在就做 | 增强元数据和分类能力 | 直接影响展示、下载和检索 |
| 接下来做 | 提升 memory / report 的检索质量 | 适合与 RAG 演进同步推进 |
| 之后再做 | 结构化对象与摘要层 | 需要建立在前两阶段之上 |
| 远期做 | 更强的 RAG / GraphRAG 联动 | 需要结构化层和检索质量稳定后再推进 |

## 10. 下一步执行建议

建议按以下顺序推进：

1. 先把共享记忆、私有记忆和报告目录的规范写清楚。
2. 再为 memory / report 设计统一的元数据最小集。
3. 评估当前报告引用链路中最脆弱的规则，并优先补强。
4. 在元数据稳定后，再开始抽取高价值结构化对象和报告摘要。
