# AgentWeave 能力扩展子系统演进路线图

## 1. 文档目标与读者

本文档用于说明 Skills + MCP 这一能力扩展层的后续演进方向，帮助项目维护者、平台开发者和新加入成员理解：

- 当前能力扩展层已经解决了什么问题
- 它现在的治理短板是什么
- 后续应先补哪些基础能力，再考虑更复杂的扩展能力

## 2. 一句话结论

能力扩展子系统当前已经完成“白名单装配 + 文件化配置 + 基础测试”的最小闭环，接下来应该优先增强治理、调试和生命周期管理，而不是急于增加更复杂的能力市场或自动发现机制。

## 3. 当前状态

当前能力扩展层具备以下能力：

- Skills 以目录和 `SKILL.md` 为中心组织
- Agent profile 显式声明允许使用的 Skill 列表
- MCP 使用 `mcp.json` 作为配置入口
- MCP 支持启用、Agent 绑定和单服务测试
- Runtime 构建时会把 Skills 与 MCP tools 一起注入
- 前端提供 Skill 列表展示和 MCP 配置编辑 / 测试面板

这说明扩展层已经可以支撑“按 Agent 定制能力”，但治理深度仍然较浅。

## 4. 当前短板

- Skills 元数据较少，难以表达风险、输入约束、适用场景和依赖信息。
- MCP 配置以文件为真源，适合本地场景，但缺少更强的审计和变更历史。
- MCP 测试状态只存在于内存中，服务重启后即丢失。
- Runtime 缓存失效粒度较粗，配置变化后通常需要整体刷新。
- 当前权限模型主要保护路由访问，但对“谁可以绑定哪些能力、谁可以改哪些扩展配置”还不够细。
- 前端主要是运维视角面板，还不是完整的能力治理工作台。

## 5. 演进原则

### 5.1 先治理后扩张

在能力扩展层，治理边界比数量更重要。应先把已有 Skills 和 MCP 的治理做稳，再扩大能力接入面。

### 5.2 保持 Runtime 装配边界清晰

无论扩展层如何演进，最终都应由后端 runtime 显式决定某个 Agent 拥有哪些能力。

### 5.3 优先低运维和可调试

当前项目定位仍以本地和示例平台为主，任何演进都应优先保证可理解、可测试、可回退。

### 5.4 配置、测试和使用要分层

保存配置、测试连通性、真正注入 runtime 是三个不同环节，后续也应保持清晰分层。

## 6. 阶段路线图

### 6.1 Phase 1：固化 Skills/MCP 的注册与绑定边界

**目标**

把当前已经存在的目录扫描、配置解析和 Agent 绑定规则文档化、规范化。

**重点**

- 统一 Skills 元数据最小规范
- 明确 MCP 配置字段与 Agent 绑定规则
- 收敛“哪些信息属于注册表，哪些信息属于 runtime”

### 6.2 Phase 2：补齐测试、调试与审计能力

**目标**

让能力扩展层更容易被排障和验证。

**重点**

- 更清晰的 MCP 健康状态和错误反馈
- 更明确的 Skills / MCP 调试输出
- 基础变更记录和测试记录

### 6.3 Phase 3：细化能力可见性、授权和生命周期管理

**目标**

让“谁能看、谁能改、谁能用”变成更明确的治理模型。

**重点**

- 细化扩展配置写权限和测试权限
- 更清晰的 Agent 绑定策略
- 更完善的启用、停用、替换和淘汰机制

### 6.4 Phase 4：为更多外部能力接入提供标准化扩展框架

**目标**

在现有 Skills + MCP 基础上，为未来更丰富的扩展形态留出统一框架。

**重点**

- 更标准的元数据规范
- 更强的扩展发现能力
- 更一致的测试、治理和接入流程

## 7. 每阶段进入条件与完成标准

| 阶段 | 建议进入条件 | 建议完成标准 |
| --- | --- | --- |
| Phase 1 | 当前扩展层已经可用，但规则主要散落在代码和经验中 | Skills / MCP 的注册、绑定和运行时边界清晰稳定 |
| Phase 2 | 基础边界稳定后，排障和验证成本开始成为主要问题 | 能更方便地判断某项扩展为何不可用、为何测试失败 |
| Phase 3 | 系统开始需要更细的权限和生命周期控制 | 扩展配置、测试、使用边界更可治理 |
| Phase 4 | 已有治理机制足够稳定，开始需要接纳更多类型的能力源 | 扩展层具备更清晰的标准化接入框架 |

## 8. 关键风险与非目标

### 8.1 关键风险

- 若元数据和治理规则继续过轻，能力增长后会难以维护。
- 若过早把扩展层做成复杂平台，会偏离当前项目的轻量定位。
- 若把运行时装配逻辑下沉到前端，会破坏能力治理边界。

### 8.2 非目标

- 当前不把能力扩展层演进成独立插件市场。
- 不在本阶段引入复杂的多租户能力分发机制。
- 不让前端直接决定 Agent 拥有哪些工具。

## 9. 推荐优先级

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 现在就做 | 固化 Skills / MCP 的最小规范 | 这是治理的基础 |
| 现在就做 | 补齐测试与错误反馈 | 当前最直接影响运维和调试效率 |
| 接下来做 | 细化权限和生命周期 | 适合在规范稳定后推进 |
| 之后再做 | 更通用的扩展框架 | 需要以前几阶段为前提 |

## 10. 下一步执行建议

建议按以下顺序推进：

1. 先整理 Skills 元数据字段和 MCP 配置字段的最小规范。
2. 再梳理 Runtime 中 Skills 与 MCP 注入的边界和缓存失效条件。
3. 补充 MCP 测试结果、错误原因和最近可用工具的更强可视化。
4. 在治理清晰后，再考虑更复杂的扩展发现和生命周期管理能力。
