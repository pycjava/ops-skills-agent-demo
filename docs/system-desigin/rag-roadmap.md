# AgentWeave RAG 演进路线图

## 1. 文档目标与读者

本文档用于说明 AgentWeave 在检索增强能力上的演进方向，回答三个问题：

- 当前为什么继续以普通 RAG 作为主方案，而不是直接切到 GraphRAG。
- 现有 RAG 的能力边界、主要短板和演进顺序是什么。
- 未来如果要进入结构化知识层和 GraphRAG，应该在什么条件下推进。

本文档同时面向三类读者：

- 产品和项目维护者：快速理解当前判断和优先级。
- 新加入项目的开发者：理解 RAG 子系统的阶段目标和技术边界。
- 后续实现人员：把路线图拆分为可执行任务时作为决策依据。

与现有文档的关系如下：

- `rag-design.md` 说明当前本地 RAG 的实现方式和边界。
- 本文档说明为什么按当前顺序演进，以及每一阶段优先补什么能力。

本文档描述的是“推荐演进路线”，不是现状清单。凡是尚未落地的能力，均在对应阶段中明确标注为后续工作。

## 2. 一句话结论

AgentWeave 当前阶段应继续以“轻量、本地、可回退”的普通 RAG 为主线，先把文档切块、索引、召回、评估和可观测性做稳，再逐步引入混合检索和结构化知识层；GraphRAG 是明确的远期阶段，但不应提前成为当前实现的主战场。

## 3. 当前状态

当前项目已经具备一个可工作的本地 RAG 增强层，主要特征如下：

- 知识源来自两类文档：会话附件和 `/memories/`。
- 文档统一标准化为 `RagSourceDocument` 后进行切块、embedding 和索引。
- 向量索引使用本地 Chroma，embedding 默认通过远程接口生成。
- 查询阶段按 `conversation_id` 和 `agent_id` 做轻量作用域过滤。
- 命中结果会被整理成 `<rag_context>` 注入聊天链路。
- 当 Chroma、embedding 或索引状态异常时，系统会自动回退到原有上下文拼接方案，不阻断聊天主流程。

这套方案的优点是成本低、接入快、适合单机和个人开发环境，已经满足“把附件与长期记忆统一纳入检索链路”的首期目标。

## 4. 当前短板

现有 RAG 已经可用，但距离“稳定、可调、可扩展”的平台能力还有明显差距，主要体现在以下方面：

- 切块策略仍较粗糙，主要依赖固定字符长度，难以适配 Markdown、日志、SQL、JSON 等不同文本结构。
- metadata 仍偏基础，缺少更明确的文档类别、标签、来源用途、质量等级等维度。
- 召回链路仍以单一向量检索为主，尚未引入关键词检索、reranker 或更细粒度的排序策略。
- 缺少系统性的检索评估样例和质量指标，调参主要依赖人工观察。
- 知识仍主要以文本块形式存在，系统对“实例、环境、凭证、任务、报告”等高价值对象的理解较弱。
- 多跳关系问题仍然依赖模型自行从若干文本片段中拼接推理，稳定性和可解释性有限。

这些短板意味着：当前最需要的不是直接引入更复杂的图谱方案，而是先把普通 RAG 的基础设施做实。

## 5. 演进原则

后续 RAG 演进建议遵循以下原则：

### 5.1 先提升当前主链路，再增加新层

优先补强已有 RAG 的切块、检索、调试和评估能力。只有当普通 RAG 的收益开始逼近上限时，再进入更重的结构化和图谱阶段。

### 5.2 优先选择低运维、可本地落地的方案

项目当前定位是示例平台和本地工作台，不应过早引入必须依赖额外服务、复杂部署或专门运维团队的重型架构。

### 5.3 保持失败可回退

任何新检索能力都应视为增强层，而不是聊天主链路的硬依赖。召回失败、索引损坏、抽取异常都不应阻断核心对话流程。

### 5.4 优先复用已存在的结构化数据

项目内已经有会话、附件、任务、任务运行、提醒、MCP 配置等结构化业务数据。后续进入结构化知识层时，应优先复用这些已存在的模型和服务边界，而不是从文本中重复抽取本来就已结构化的信息。

### 5.5 用进入条件控制阶段升级

每一阶段都应有清晰的进入条件和完成标准，避免把“未来方向”混成“当前必做项”。

### 5.6 让质量评估先于复杂度增长

只有在检索质量、问题类型和真实收益都有证据支撑时，才进入更复杂的阶段。复杂架构不能代替评估。

## 6. 阶段路线图

### 6.1 Phase 1：强化现有向量 RAG

**阶段目标**

把当前“可用”的向量 RAG 提升为“稳定、可调、可观测”的基础能力层。

**为什么先做这一阶段**

当前系统最大的瓶颈不是缺少图谱，而是检索基础设施还不够成熟。若在此阶段直接进入 GraphRAG，会把问题从“召回质量不稳定”升级为“召回、抽取、建图、遍历全都不稳定”。

**建议新增的能力**

- 按文档类型升级切块策略，例如分别优化 Markdown、日志、SQL、JSON 和报告类文本的切块方式。
- 为 chunk 补充更清晰的 metadata，例如文档类别、来源域、用途标签、时间信息和可见范围。
- 提升索引状态与调试能力，例如记录文档数、chunk 数、最近重建信息、典型查询命中情况。
- 建立小规模评估样例集，用固定问题验证检索是否命中正确附件、memory 或报告片段。
- 在不改变主聊天体验的前提下，继续保持失败可回退的机制。

**该阶段的主要风险**

- 过早引入过多可选参数，导致配置复杂度上升。
- 文档类型识别和切块规则不稳定，造成索引结果前后不一致。

**完成后的预期效果**

- 团队可以更稳定地回答“当前为什么命中了这段文本，为什么没命中那段文本”。
- RAG 质量提升不再主要依赖人工直觉，而有基本的样例和指标支撑。

### 6.2 Phase 2：升级为混合检索和更强可观测性

**阶段目标**

在保持低运维前提下，把召回从“单一向量相似度”升级为“语义 + 关键词”的混合检索，并补上排序、去重和质量观测能力。

**为什么这一阶段排在 GraphRAG 之前**

很多检索问题并不是缺少图结构，而是关键词和结构线索没有被有效利用。例如实例 ID、文件名、报错码、SQL 片段、区域代号这类信息，往往更适合通过关键词或精确匹配召回。

**建议新增的能力**

- 引入关键词检索能力，例如基于轻量 BM25 或 SQLite FTS 的本地检索层。
- 将向量检索与关键词检索结果合并，形成统一排序。
- 在必要时增加 reranker，用于改善前几条结果的最终顺序。
- 对不同来源采用不同召回策略，例如附件、memory、报告可以有不同的召回阈值和排序逻辑。
- 增强可观测性，记录检索命中率、来源分布、去重前后结果数量和 rerank 前后变化。

**该阶段的主要风险**

- 检索链路变长后，调试复杂度明显提升。
- 如果没有评估集支撑，可能只是“看起来更复杂”，但未必真的提高答案质量。

**完成后的预期效果**

- 包含明确关键词的问题能更稳定命中。
- 系统在“自然语言问题”和“半结构化关键词问题”之间的表现更均衡。

### 6.3 Phase 3：引入结构化知识层

**阶段目标**

让系统开始识别和管理高价值对象，把一部分核心知识从“文本块”提升为“结构化实体与关系”，但暂不进入完整 GraphRAG。

**为什么这一阶段必须先于 GraphRAG**

GraphRAG 的前提不是“有很多文档”，而是“有一批值得做图的稳定实体和关系”。如果 Phase 3 没有做好，GraphRAG 的图只能建立在不稳定抽取结果之上，维护成本会很高。

**建议新增的能力**

- 从长期记忆、巡检报告、云上下文解析结果中抽取高价值对象，例如实例、账号、环境、区域、报告、任务、运行记录。
- 为这些对象建立结构化表示，优先复用现有 ORM 模型和服务层边界。
- 让聊天链路在适合时先查结构化对象，再回退到文本检索。
- 对结构化结果提供清晰引用来源，避免“只有结论，没有证据”。

**该阶段的主要风险**

- 抽取规则和业务模型边界不清，导致结构化对象质量参差不齐。
- 结构化层和文本层重复维护同一事实，带来一致性问题。

**完成后的预期效果**

- 对“某实例属于哪个环境”“某报告对应哪个任务运行”“某凭证关联哪些实例”这类问题，系统能更稳定地回答。
- 文本检索开始承担补充证据的角色，而不是所有问题都只能靠文本块拼接。

### 6.4 Phase 4：引入 GraphRAG

**阶段目标**

为高价值、多跳关系问题提供图检索与图推理能力，使系统不仅能找到相关文本，还能沿着关系链定位关键节点和证据。

**为什么它是明确的远期阶段**

GraphRAG 的收益主要出现在关系密集、需要多跳推理、需要解释“结论是如何沿关系链得出的”的场景。它的前提条件、实施复杂度和维护成本都显著高于前几个阶段，因此应在结构化知识层稳定后再进入。

**建议新增的能力**

- 从结构化对象和部分高价值文本中抽取关系，构建可检索的图。
- 围绕特定问题类型执行子图检索，而不是对所有知识源做全域图化。
- 将图结果与文本证据一起注入模型，让回答既有关系链，也有原始引用片段。
- 为图构建和图更新建立清晰的重建、修复和回退机制。

**该阶段的主要风险**

- 关系抽取错误会沿图传播，影响多个问题。
- 图更新链路变长后，索引维护、数据一致性和调试成本显著上升。
- 如果问题类型不够集中，GraphRAG 的复杂度可能高于实际收益。

**完成后的预期效果**

- 系统能更稳定处理跨文档、多对象、多步骤的关系型问题。
- 回答结果的“关系路径”比纯文本 RAG 更清晰、更可解释。

## 7. 每阶段的进入条件与完成标准

| 阶段 | 建议进入条件 | 建议完成标准 |
| --- | --- | --- |
| Phase 1 | 当前本地 RAG 已经接入聊天主链路，主要痛点集中在召回稳定性和调参困难 | 已具备基础评估样例、可解释的索引状态、按文档类型优化的切块和更清晰的 metadata |
| Phase 2 | Phase 1 已能稳定复现和定位召回问题，且出现大量关键词类漏召回 | 已具备混合检索、统一排序、可选 reranker 和更完整的检索观测指标 |
| Phase 3 | 混合检索已把普通文档召回做稳，但高价值对象问题仍依赖模型自行拼接 | 已形成一批稳定的结构化对象，并能在聊天链路中优先复用结构化结果 |
| Phase 4 | 已存在高频多跳关系问题，且结构化对象与关系模型足够稳定 | 已能在有限高价值场景下完成图构建、子图检索、文本证据混合注入和失败回退 |

建议把“进入下一阶段”视为显式决策，而不是自然滑动。每次阶段升级前，都应重新确认两个问题：

- 当前阶段的主要收益是否已经兑现。
- 下一阶段带来的复杂度是否有足够的业务价值支撑。

## 8. GraphRAG 远期方案

GraphRAG 在 AgentWeave 中适合聚焦于以下问题类型：

- 某实例与哪组云凭证、哪个环境、哪些巡检任务、哪些报告、哪些历史异常相关。
- 某次任务失败后，关联了哪些执行记录、报告结论、补救动作和后续提醒。
- 某个复杂排障问题需要跨多个 memory 文档、报告和业务对象串联证据。

在这些场景下，GraphRAG 的潜在收益包括：

- 更适合多跳关系问答，而不是只找局部相似文本。
- 更容易把“为什么得出这个结论”解释为一条关系链。
- 可以把部分跨文档拼接工作从模型隐式推理转移到显式图检索。

但它带来的额外成本也必须被显式承认：

- 需要稳定的实体与关系抽取链路。
- 需要额外的图存储、图更新、图调试和图重建机制。
- 需要更严格的质量验证，否则图中的错误会扩大影响面。

因此，GraphRAG 在本项目中的推荐落地方式不是“全项目统一图化”，而是“围绕高价值场景做局部图化”，例如优先覆盖“实例-环境-凭证-任务-报告”这一类关系密集链路。

## 9. 推荐优先级

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| 现在就做 | 更好的切块策略 | 这是当前检索质量的基础设施，收益直接且风险可控 |
| 现在就做 | metadata 丰富化与文档分类 | 有助于排序、过滤、调试和后续阶段升级 |
| 现在就做 | 检索调试接口与评估样例 | 没有评估就无法判断演进是否有效 |
| 接下来做 | 混合检索 | 适合解决实例 ID、报错码、文件名等强关键词问题 |
| 接下来做 | 可选 reranker | 应建立在评估基础上，作为质量提升器而不是默认依赖 |
| 之后再做 | 结构化知识层 | 需要先明确高价值对象和现有模型边界 |
| 远期做 | GraphRAG | 适合多跳关系场景，但前置条件和维护成本都更高 |
| 暂不优先 | 全域图化 | 对当前项目规模和运维目标不划算 |
| 暂不优先 | 重型分布式向量库 | 当前定位仍以本地、轻量和示例平台为主 |

## 10. 下一步执行建议

如果要从当前仓库状态继续推进，建议按以下顺序落地：

1. 先补 Phase 1 的基础能力：
   - 梳理附件、memory、报告三类文本的切块策略。
   - 明确 chunk metadata 规范。
   - 补齐检索调试输出和最小评估样例集。

2. 再推进 Phase 2：
   - 为强关键词场景引入轻量关键词检索层。
   - 设计统一的结果合并、排序和去重逻辑。
   - 评估是否真的需要 reranker，而不是默认引入。

3. 然后评估 Phase 3：
   - 列出最值得结构化的对象清单。
   - 明确哪些关系来自已有 ORM，哪些需要从文档中抽取。
   - 让结构化查询先覆盖少量高价值问答，再逐步扩大范围。

4. 最后再考虑 Phase 4：
   - 先挑选一条高价值、多跳、可验证的关系链路做试点。
   - 证明 GraphRAG 相比普通 RAG 和结构化查询确实有明显收益后，再决定是否继续扩展。

总体建议是：把 GraphRAG 当成明确的远期能力目标，但不要把它当成当前阶段的默认解法。对 AgentWeave 来说，最现实的路径仍然是“先把普通 RAG 做强，再进入结构化，再进入 GraphRAG”。
