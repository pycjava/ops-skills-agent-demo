# `using-superpowers` Skill 设计说明

## 1. Skill 定位

`using-superpowers` 是本项目中最特殊的 Skill。它不是某个业务领域的“能力 Skill”，而是一个**流程治理 Skill**，用于约束 Agent 在开始任何任务前如何判断“是否应该使用其他 Skill”。

它解决的问题不是“怎么排障”，而是“什么时候必须切换到正确的技能体系去做事”。

## 2. 设计目标

- 在任何可能用到 Skill 的场景下，优先触发 Skill 判断，而不是先凭经验行动。
- 让 `router`、`supervisor` 和叶子 Agent 都遵循相同的 Skill 调用纪律。
- 明确用户指令、仓库级规则与 Skill 规则之间的优先级。

## 3. 适用场景

该 Skill 适用于：

- 新会话开始时判断是否需要其他 Skill。
- 任何用户任务到来时，在真正执行前先做 Skill 命中判断。
- 在提问、澄清、代码探索、计划制定之前先检查可用 Skill。

它不直接适用于：

- 被明确派发执行某个具体任务的子 Agent。
- 已经确定正在执行的领域 Skill 内部步骤本身。

## 4. 核心规则

### 4.1 先判定，再行动

`using-superpowers` 的核心原则是：

- 只要有哪怕极小概率某个 Skill 适用，就必须先使用相应 Skill。
- 不允许先做 repo 探索、先回答、先澄清，再回头补 Skill。

这是一个强约束流程，而不是建议。

### 4.2 流程图高于摘要

该 Skill 内含 DOT 决策流程图，并声明：

- 流程图是权威执行规范。
- 摘要、记忆或概括性描述只能补充说明，不能覆盖流程图分支。

这意味着它不是普通的文字说明，而是“流程规范文件”。

### 4.3 优先级模型

该 Skill 明确了优先级：

1. 用户显式指令、`AGENTS.md` 等仓库规则。
2. `using-superpowers` 等 Skill 规则。
3. 平台默认行为。

因此，它会强制 Skill 使用纪律，但不会覆盖用户明确要求。

## 5. 在本项目中的运行位置

当前所有公开 Agent 都绑定了 `using-superpowers`，但用途略有不同：

- `router`：用它来约束“先判断是否需要技能路由”。
- `supervisor`：用它来约束“复杂编排前先判断是否要调用其他 Skill”。
- `general` / `dba` / `ops`：用它来约束“开始执行领域任务前先命中正确 Skill”。

因此，它是全局流程规范的一部分。

## 6. 标准执行流程

```text
收到用户消息
  -> 判断是否可能有 Skill 适用
  -> 如果有，先使用对应 Skill
  -> 宣告正在使用哪个 Skill 做什么
  -> 如 Skill 有清单，则建立任务清单
  -> 按 Skill 规则继续执行
```

设计目的：

- 防止 Agent 因“任务看起来简单”而跳过 Skill。
- 保证流程、知识和工具使用方式都来自最新 Skill 文档，而不是模型记忆。

## 7. 与其他 Skill 的关系

`using-superpowers` 不替代其他 Skill，而是负责把 Agent 引导到正确 Skill。

例如：

- 用户说“帮我查 Docker 容器为什么重启”，它会推动 Agent 使用 `docker`。
- 用户说“分析这条 MySQL SQL 为什么慢”，它会推动 Agent 使用 `mysql-sql-analyzer`。
- 用户说“帮我整理成 Obsidian 文档”，它会推动 Agent 使用 `obsidian-markdown`。

## 8. 与平台适配的关系

该 Skill 原始说明来自更通用的技能系统，因此提供了平台映射说明，告诉 Agent：

- Skill 中提到的 `TodoWrite` 对应当前平台的计划工具。
- Skill 中提到的文件读写、shell、子 Agent 派发，应映射到当前平台等价能力。

这让 Skill 规则可以跨平台复用，同时保留当前仓库的实际工具约束。

## 9. 安全与治理价值

从治理角度看，这个 Skill 的价值主要体现在：

- 防止“绕过 Skill 直接做事”，导致流程不一致。
- 防止 Agent 用过期记忆代替当前 Skill 文档。
- 让编排和执行过程具有更强可解释性。

## 10. 失败场景与兜底

- 如果不存在合适 Skill，则按平台默认能力继续处理。
- 如果 Skill 明显不适用，可结束该 Skill 的影响并回到正常流程。
- 如果用户明确要求不走某种流程，应以用户指令为准。

## 11. 设计取舍

- 它提高了流程一致性，但会增加执行前置判断成本。
- 它强化了 Skill 治理，但也要求 Skill 文档本身保持高质量和持续更新。
